# Artifacts

Each run writes one directory under `artifact_dir`:

```text
artifacts/<test_id>/
  manifest.json
  samples.ndjson
  leader-sends.ndjson
  leader-runs.ndjson
  leader-slots-snapshot.json
  leader-slots-snapshot-<start_slot>.json
  rpcedge-observations/entries.ndjson
  summary.json
  summary.md
  entry-placements.ndjson
  report.json
  report.md
  report.html
  tail-events.json
  tail-events.csv
  tails.html
  comparison.json
  comparison.md
  comparison.html
  index.html
  paired-rows.json
  paired-rows.csv
```

## manifest.json

Run-level metadata:

- schema version;
- generated timestamp;
- redacted RPC URL label;
- payer pubkey;
- count/rate settings;
- transaction fee settings;
- resend attempt settings;
- provider names and kinds.

Do not put API keys, private keys, or full secret-bearing URLs into the
manifest.

## samples.ndjson

One JSON object per transaction/provider attempt. This is diagnostic sender
metadata, not the primary latency report.

Important fields:

- `test_id`
- `iteration`
- `signature`
- `provider_name`
- `provider_kind`
- `accepted`
- `client_started_at`
- `client_finished_at`
- `client_ack_latency_us`
- `provider_send_started_at`
- `provider_send_finished_at`
- `provider_ack_latency_us`
- `provider_request_id`
- `returned_signature`
- `status_code`
- `error_class`
- `error`
- `resend_attempt_index`: zero-based resend attempt, present for
  `run-leader-paced`;
- `resend_attempts`: total configured attempts for that signed transaction;
- `resend_interval_ms`: intended spacing between attempts;
- `route_policy`
- `selected_routes`
- `leader_client_family`
- `leader_software_client`
- `leader_software_client_id`

`provider_ack_latency_us` is useful for diagnosing provider/API behavior, but it
is not landing latency and not first-shred/deshred/processed latency.
`client_ack_latency_us` is the elapsed wall time for the full client submission
round for that transaction and can include concurrent fanout effects.

When `run-leader-paced --resend-attempts N` is used, `samples.ndjson` can have
multiple rows with the same `signature`. These rows are per-attempt ACK
diagnostics. Landing reports deduplicate by caller signature before calculating
success and latency.

`leader_client_family` is a coarse cohort label. Route-policy decisions should
prefer `leader_software_client` and `leader_software_client_id` when present.

## leader-sends.ndjson

Generated by `run-leader-paced`.

One JSON object per signed benchmark transaction:

- `test_id`
- `iteration`
- `signature`
- `leader_identity`
- `leader_run_start_slot`
- `leader_run_end_slot`
- `send_slot`
- `sent_at`
- `trigger_source`: `grpc_slot` or `rpc_poll`
- `slot_signal_status`
- `slot_signal_observed_at`
- `leader_client_family`
- `leader_software_client`
- `leader_software_client_id`
- `route_policy`
- `selected_routes`

This file is the public join surface for later leader-cohort enrichment.

Paired-provider sends also record `payer_pubkey`, `recent_blockhash`, and the
verified leader network-path/stake/location fields used at send time.

## leader-runs.ndjson

One decision per observed contiguous leader run, including runs skipped by
`--leader-network-path-class`. Each row stores route class, verification and
observation time, RTT evidence, stake/location context, eligibility, and a
stable skip reason. It is the denominator for actual run-window leader-run and
scheduled-slot coverage.

## leader-slots-snapshot.json

Generated by `run-leader-paced --capture-leader-slots`.

This file stores the exact JSON-RPC `getLeaderSlots` response captured for the
run in `rpc_poll` mode. In default `grpc_slot` mode, rolling refreshes
are stored as `leader-slots-snapshot-<start_slot>.json`. These files are the
portable cohort-enrichment source for standalone reports.

Top-level fields:

- `schemaVersion`
- `fetchedAt`
- `rpcUrlLabel`, with query strings removed
- `startSlot`
- `limit`
- `response`, the raw JSON-RPC response body

When captured from RPCEdge, `response.result.data[]` can include:

- leader identity and stake;
- data center, city, country, region, and coordinates;
- validator client family/software/version;
- route hints;
- historical landing-latency profiles.

Do not fetch a fresh leader schedule when regenerating a historical report. Use
the saved snapshot so the report reflects what was known during the run.

## Observation Events

The RPCEdge collector and any external observation collectors should emit
newline-delimited `ObservationEvent` JSON.

Fields:

- `schema_version`
- `test_id`
- `signature`
- `source_name`
- `source_kind`: `yellowstone_processed`, `yellowstone_deshred`, or
  `ndjson_import`
- `observed_at`
- `submitted_at`
- `slot`
- `slot_index`
- `source_sequence`

Example:

```json
{"schema_version":1,"test_id":"run-a","signature":"5abc...","source_name":"direct-deshred","source_kind":"yellowstone_deshred","observed_at":"2026-06-29T12:00:00.001Z","submitted_at":"2026-06-29T12:00:00.000Z","slot":429000000,"slot_index":12,"source_sequence":null}
```

## observation-summary.json

Generated by `summarize-observations`.

Source-level outputs:

- observed count;
- missing from matched signatures;
- first-seen count;
- first-seen share;
- submit-to-observed p50/p75/p90/p95/p99/max.

Pair-level outputs:

- matched count;
- win count by source;
- same-timestamp count;
- p50/p75/p90/p95/p99/max delta.

Positive pair delta means `from_source` observed before `to_source`.

## matched-observations.ndjson

Generated by `run-leader-paced --collect-rpcedge`.

This is the RPCEdge observation stream filtered down to signatures generated by
the benchmark run. The runner injects the local benchmark `submitted_at`
timestamp before producing matched summaries.

## matched-observation-summary.json

Generated by `run-leader-paced --collect-rpcedge`.

This is the headline public benchmark summary for the run. It uses only
benchmark-generated signatures, not unrelated stream traffic.

## rpcedge-observations/entries.ndjson

Generated only when `run-leader-paced --collect-rpcedge --collect-entries` or
`collect-rpcedge --collect-entries` is used.

This file contains slot-wide Yellowstone entry updates. It is not filtered by
benchmark signature.

Fields:

- `schema_version`
- `test_id`
- `source_name`
- `source_kind`: `yellowstone_entry`
- `observed_at`
- `slot`
- `entry_index`
- `num_hashes`
- `entry_hash`
- `executed_transaction_count`
- `starting_transaction_index`

Entry updates are block-placement context. They are not proof of when the
transaction packet reached the leader.

## entry-placements.ndjson

Generated by `run-leader-paced --collect-rpcedge --collect-entries` after
`matched-observations.ndjson` exists.

Each row is a benchmark signature whose processed Yellowstone transaction
metadata carried a `slot_index` that could be joined to a captured entry range.

Fields:

- `signature`
- `signature_role`
- `caller_signature`
- `slot`
- `slot_index`
- `entry_index`
- `tx_index_in_entry`
- `entry_num_hashes`
- `entry_hash`
- `entry_executed_transaction_count`
- `entry_starting_transaction_index`

Use this for "how early in the produced block did the transaction land?" Do not
call `entry_index` an exact PoH tick. Exact tick buckets require additional
derivation from the full entry/tick sequence or an external block-building
dataset such as IBRL.

## summary.json

Machine-readable summary grouped by provider:

- count;
- accepted;
- errors;
- min;
- p50;
- p75;
- p90;
- p95;
- p99;
- max.

Percentiles in `summary.json` are based on accepted provider ACK latency and
should be treated as diagnostic only. Percentiles in
`observation-summary.json` are the benchmark result.

## summary.md

Human-readable version of `summary.json`.

## report.json / report.md / report.html / tail-events.*

Generated by:

```bash
solana-tx-bench report --artifact-dir artifacts/<test_id>
```

The report is intentionally self-contained. It reads only local files in the
artifact directory:

- `samples.ndjson`
- `leader-sends.ndjson`
- `matched-observations.ndjson`
- `entry-placements.ndjson`
- `leader-slots-snapshot.json`
- `leader-slots-snapshot-<start_slot>.json`

Leader cohorts are derived from the saved JSON-RPC `getLeaderSlots` responses.
Do not join ClickHouse or fetch a new leader schedule when regenerating a
public report for a historical run.

`tail-events.json`, `tail-events.csv`, and `tails.html` are derived from the
slowest first-observed landing events. Tail rows include:

- full signature;
- first observation source and latency;
- policy arm, route policy, selected routes, and comparison group;
- send slot, send leader, and send leader client;
- landed slot, landed leader, and landed leader client;
- first-observed slot index when available;
- processed Yellowstone/gRPC slot index when available;
- entry index, transaction index inside entry, and entry transaction count when
  `entry-placements.ndjson` exists;
- compute-unit price;
- base fee, priority fee, transaction fee;
- route-tip generated lamports, route-tip landed lamports, and generated vs
  landed total spend.

Use the processed slot index for block-position analysis regardless of which
configured receiver was first. The earliest receiver observation is the
landing clock; processed gRPC is the canonical transaction metadata clock.

Cost fields are explicit:

- `base_fee_lamports`
- `priority_fee_lamports`
- `transaction_fee_lamports`
- `route_results[].route_tip_lamports` for route-tip generated spend
- report-level `route_tip_landed_lamports` fields for route tips whose
  signatures were actually observed

When an RPCEdge QUIC provider is configured with `route_results: true`,
`samples.ndjson` may also include:

- `route_results_complete`: whether the relay returned route attempts before
  the bounded detailed-ACK timeout.
- `route_results[]`: one row per backend route attempt, including `route`,
  `route_name`, `provider`, `accepted`, `latency_us`, compact `error_class`,
  `bundle_id`, and route-added tip fields.
- `route_results[].route_tip_signature`,
  `route_results[].route_tip_lamports`, and
  `route_results[].route_tip_account`: exact route-added Jito tip metadata when
  the relay's `jito_bundle` route created a separate tip transaction.

Route-tip generated spend is not the same as landed route-tip spend. Generated
means the relay returned a tip transaction signature for the route. Landed means
that signature appears in `matched-observations.ndjson`. Because RPCEdge
observation subscriptions are account-filtered, the collector subscribes to the
benchmark payer plus built-in provider observer accounts. Jito's tip accounts
are built in. Add accounts to the provider observer list when adding another
tip-based sender adapter, or pass `--observation-account <pubkey>` for a
one-off private account.

## comparison.json / comparison.md / comparison.html / index.html

Generated by:

```bash
solana-tx-bench compare \
  --artifact-dir artifacts/<run-a> \
  --label "Run A" \
  --artifact-dir artifacts/<run-b> \
  --label "Run B" \
  --output-dir docs/reports/<comparison-slug>
```

The comparison report is also self-contained. It reads only each run's local
artifact directory and writes a static `index.html` suitable for GitHub Pages.

For route-policy comparisons, prefer artifacts produced by:

```bash
solana-tx-bench run-leader-paced \
  --route-strategy paired_route_policies \
  --slot-trigger grpc_slot \
  --capture-leader-slots \
  --collect-rpcedge
```

Paired samples include:

- `comparison_group_id`: same leader run and same slot signal.
- `policy_arm`: stable policy arm name, for example `tpu_quic_only`,
  `always_race`, or `software_client_aware`.
- `policy_arm_index`: stable arm index before per-group order rotation.

Compare policies within `comparison_group_id`. Separate 5-minute artifact
directories for TPU-only and always-race are valid route smoke tests, but they
are not valid A/B performance comparisons.

For a two-arm artifact, `compare` adds `paired-rows.json` and
`paired-rows.csv`. Each row is one comparison group and observation source,
with both signatures, leader/path context, complete or one-sided status, both
latencies, and `candidate - baseline` latency, landed-slot, and block-position
deltas. Receiver-specific rows are retained for diagnosis. Public transaction-
sender reports must collapse them to the earliest observation per signature
before calculating a single route/provider timing delta.

The scoring model reports five buckets:

- landing latency in milliseconds;
- landing latency in slots;
- processed block position;
- same-slot landing rate;
- observed success ratio.

Provider ACK latency is included only as a diagnostic column and is not part of
landing proof. Compare only runs with the same transaction shape, sender region,
slot trigger, observation source, and fee/tip policy unless the report is
explicitly exploratory. Clean route-policy baselines use the same compute-unit
limit and compute-unit price in every policy arm; fee ladders and retry/spam
strategies are separate experiments.

## Schema Compatibility

The artifact schema is intentionally append-only. Downstream analyzers should
ignore unknown fields so future versions can add:

- confirmation observation IDs;
- provider route details;
- request size;
- response size;
- landed-slot enrichment.
- leader-slot enrichment snapshots;
- gRPC slot trigger details.
